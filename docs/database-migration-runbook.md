# 数据库迁移操作规范

## 当前迁移方式

- 新库以 `springboot-backend/src/main/resources/db/init.sql` 建表，再按 `README.md` 导入所需种子数据。
- 旧库升级时，由操作者按文件名顺序执行 `springboot-backend/src/main/resources/db/migrations/` 中尚未执行的脚本。
- Spring SQL 初始化在开发和生产配置中均为 `never`；应用启动不会自动执行迁移。
- 当前项目没有 Flyway、Liquibase 或应用内迁移版本账本。不要仅凭文件名、Git 提交时间或应用能启动，就认定某份迁移已经执行。

旧迁移采用日期加描述的文件名，例如 `20261001_add_story_discovery_index.sql`。已有文件属于历史记录：一旦交付或在任何数据库执行，不要原地修改；需要修正时新增后续迁移。

## 执行前检查

1. 确认目标数据库、当前代码版本和要升级的目标版本，确认当前连接没有指向生产库或其他玩家数据。
2. 完成可恢复的数据库备份，并确认备份文件可读取。DDL 在 MySQL 中通常会隐式提交，不能依赖事务回滚。
3. 对照每个待执行脚本检查目标表、列、索引和静态配置的现状。仓库没有自动历史账本时，必须以数据库实际结构和数据核对结果判断是否待执行。
4. 先在数据库副本演练。记录执行文件名、开始时间、结果、执行人和验证结果；失败后先检查数据库实际状态，再决定修复方式，不能直接从头重跑。
5. 每次只执行一份脚本，成功并完成脚本内的验证后再继续下一份。

## 新迁移编写规则

1. 使用唯一文件名 `YYYYMMDD_简短英文描述.sql`，按字典序执行；一个文件只处理一个逻辑变更。
2. 文件开头说明变更目的、影响范围、是否涉及玩家数据、重复执行行为和执行后检查方法。
3. 优先采用向前兼容的新增列、表、索引或静态配置。避免把无关重构、清理和玩法调整塞进同一迁移。
4. 对 DDL 明确前置条件和重复执行行为。MySQL 版本不支持目标语法时，使用限定当前 schema 的 `information_schema` 检查后再执行；不能假定所有语句都支持 `IF NOT EXISTS`。
5. 静态配置更新应使用明确主键/业务键作为条件，避免覆盖管理员或运营人员已经调整的内容。种子数据和升级迁移需要保持同一份业务定义，并配套一致性检查。
6. 不在迁移里重置、删除或批量改写玩家存档、资源、战斗记录。确有业务需要时，拆成单独变更，先写出范围查询、数量核对、备份与恢复步骤，再评审。
7. 更新新库基线 `init.sql` 时，同时提供旧库升级迁移；只修改其中一处会让新旧数据库结构漂移。
8. 对迁移增加自动化检查，至少覆盖文件命名唯一、关键静态配置与基线一致、迁移没有越界修改玩家数据，以及脚本声明的重复执行行为。

## 本仓库旧库的特殊注意事项

现有迁移并非都可重复执行。例如 `20260924_battle_request_idempotency.sql` 直接添加列和唯一索引，重复执行会失败。其他脚本虽然包含 `INSERT IGNORE` 或 `UPDATE`，也可能覆盖静态配置，因此不能只按“看起来幂等”就重复运行。

本机数据库检查到 `player_resource_transactions` 表存在，但没有发现 Flyway、Liquibase 或 `schema_migrations` 类历史表；`player_action_receipts` 表也未发现。这个信息只能证明当前结构不完整或迁移状态未记录，不能据此推断一整段迁移的执行边界。本次检查是只读的，没有应用任何数据库脚本。

## 迁移账本的后续方向

后续应在充分盘点开发库和部署库的实际结构后，引入统一迁移版本账本，并为各环境建立准确基线。首次接入时不能把历史迁移全部标记为已执行，也不能在没有核对的情况下自动重放历史脚本。账本方案确定前，继续按上面的人工检查与执行记录流程操作，不要让应用启动自动修改数据库。
