# 玩家端状态职责

## Vue Query：服务端数据

- 启动档案和各功能面板的 API 响应由 Vue Query 缓存；启动档案 key 按账号 ID 区分，功能面板 key 按面板和角色 ID 区分。
- 成功执行写操作后，让对应查询失效并重新读取服务端结果。不要在 Pinia 再建一份平行的任务、首领或功能面板数据。
- WebSocket 收到任务完成、首领状态变化时，失效当前角色的对应查询；玩家切换账号后不能复用另一账号的启动缓存。
- 查询 key 放在 `src/api/queryKeys.ts` 或紧邻该功能的查询定义中，必须包含决定响应归属的账号/角色标识。

## Pinia：客户端跨组件状态

- `authStore` 管理当前登录凭证和用户身份。
- `uiStore` 管理弹窗与局部界面状态；`realtimeStore` 管理连接状态；`chatStore` 管理本次页面会话中的实时消息。
- `gameStore` 目前仍为 HUD、日志、Bootstrap 兼容投影和少量被组件实际读取的摘要服务。新功能不应把整个 API 响应再复制进一个新 Pinia store；修改现有投影时同步考虑后续迁移到 Vue Query。
- 请求幂等键、待处理战斗/剧情动作属于浏览器恢复状态，继续使用相应的 sessionStorage/localStorage 工具；它们不是服务端数据缓存。

## 实时事件与写操作

1. 服务器是玩家档案、任务、灾厄和背包等数据的事实来源。
2. Vue Query 请求并缓存服务端快照；Pinia 只保存界面真正跨组件共享的客户端状态及暂时保留的旧组件投影。
3. 普通写操作成功后失效相关查询；任务完成和灾厄变化这两类 WebSocket 事件也刷新当前角色的对应查询。
4. 不同时维护两份可变服务端摘要。当前已移除未被界面读取的 `playerStore`、`questStore` 和 `worldBossStore`；任务和灾厄面板改由查询缓存刷新。

## 本轮保留的兼容边界

`gameStore.player` 仍供顶栏、战斗属性和动作日志组件读取，`GameView` 也暂时把启动查询结果投影到该 store。把所有消费者迁到 Vue Query 需要跨多个面板逐步进行；迁移时每次只改一条数据流，并用实际 UI 流程验收。
