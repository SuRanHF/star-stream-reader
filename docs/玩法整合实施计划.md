## 1. 项目目标

把现有《星流读者》逐步打磨成以“探索升级”为主循环的多人文字 RPG：借鉴《灵界》清晰、轻操作、日志驱动的游玩节奏，同时把题材、角色成长和叙事核心放在《全知读者视角》的故事、传说、位格与选择上。

目标体验可以概括为：

> 玩家通过探索获得成长资源、装备线索和故事线索；战斗多数自动结算并写入历程；玩家在少数关键节点做选择，选择只改变自己的后续时间线；所有玩家仍处于同一个可见的大世界，并能通过公共事件留下集体影响，但不会替别人决定个人剧情。

本计划优先打磨桌面端主流程与规则。移动端适配不作为第一阶段的验收门槛。

## 2. 已确认的设计边界

| 议题 | 采用规则 | 明确不做 |
|---|---|---|
| 世界结构 | 全体玩家共享一个世界背景、公共事件与可见世界状态 | 把每个人做成互不相干的单机存档世界 |
| 玩家时间线 | 每个玩家保存自己的剧情旗标、遭遇、选择和后果 | 让先入坑玩家替新玩家改写个人剧情或封锁主线 |
| 探索 | 探索是主要行动入口，也是经验、货币、材料、装备与故事线索的主要来源 | 资源、剧情、战斗各做各的，彼此没有回流 |
| 普通战斗 | 轻操作、自动结算；结算重点放进战斗日志，辅以简短提示 | 每场普通战斗都弹出多个阻断流程的结果窗口 |
| 重要战斗 | 首领、章节节点等少数战斗允许玩家作关键准备或选择 | 让普通遭遇也变成繁琐的回合操作 |
| 故事选择 | 先给模糊征兆；玩家调查后逐渐看懂代价与来由；后果作用于自己的后续 | 开局剧透全部克制关系，或让剧情选择直接改写其他玩家支线 |
| 世界干扰 | 公共舞台、限时事件、集体讨伐等由所有人共同推进；个人剧情选择是私有因果 | 让排行榜领先者单方面触发全服不可逆剧情锁定 |
| 玩家对比 | 多分类榜单、分段/赛季与可追赶路径；主要奖励荣誉和少量资源 | 让早入坑者靠累计时长永久碾压新人 |
| 战斗策略 | 位格、装备/技能、传说或故事之间的关系、遭遇场景都可以参与判定；规则可解释且有反制 | 继续把全部克制简化为“装备某称号标签就固定增伤” |

## 3. 玩家主循环

```text
选择场景与探索行动
        ↓
消耗行动资源，触发资源 / 遭遇 / 战斗 / 故事 / 线索事件
        ↓
自动结算战斗或完成一次关键选择
        ↓
资源、经验、物品、剧情旗标写入玩家状态；完整结果写入历程
        ↓
升级、整理装备技能、解锁新的地点/难度/故事调查
        ↓
回到探索；达到条件后参与组队秘境或共享公共事件
```

### 3.1 一次探索至少要回答的问题

1. **我为什么去这里？** 场景显示推荐位阶/风险、可遇到的事件倾向、主要产出和已知线索。
2. **我付出了什么？** 行动资源或次数在服务端校验并扣除，重复请求不能重复扣费或重复发奖。
3. **发生了什么？** 事件归类清楚：战斗、故事、资源、奇遇、NPC、首领线索或暂无线索。
4. **我得到了什么？** 经验、货币、故事碎片、材料、装备和旗标均进入正确状态；结算摘要与详细历程一致。
5. **下一步有什么变化？** 状态面板、地点解锁、任务目标或后续故事明确反映本次结果。

以下是本轮查看代码后的起始判断；具体文件和行为在实现阶段仍需结合当前工作区改动复核。

| 系统 | 已有基础 | 缺口/风险 | 计划处理 |
|---|---|---|---|
| 探索 | 后端探索服务处理事件奖励；故事选择会生成玩家故事记录，保存选项、后果与奖励快照 | 探索到战斗、奖励、日志、任务/成长之间仍需按真实流程逐条验收 | 第一阶段先画出并测试完整数据流，不先推倒重写 |

### 第一轮必须先确认的交互故障

- 点一次战斗后按钮能否恢复可用，不能永久停留在“战斗中”。

## 5. 规则蓝图

### 5.1 属性、位格与成长分层

不要把所有成长塞进一个“战力”。建议拆成四层，先盘点现有字段和存档兼容性，再定最终字段名与公式：

1. **战斗基础属性**：参考原著中的力量、体力、敏捷、魔力等概念，最终中文名、作用和数值范围必须对照项目内小说文本核实。每项属性都要有明确战斗作用，避免只加面板数字。
2. **位格/阶段**：表示角色处在什么成长阶段，控制可挑战内容、技能/装备门槛和世界认知；它不是每场战斗的唯一胜负判定。
3. **能力构筑**：装备、技能、传说/故事能力提供不同解法；同一套基础属性允许不同构筑，而不是只有一条最优堆数值路线。
4. **叙事状态**：个人故事旗标、已知线索、与特定故事/人物的关系、世界线后果。这些优先影响事件可见性和后续选择，不做成可随意刷高的裸战力属性。

资源也需要做“来源—用途—上限/回收”表。至少覆盖经验、普通货币、故事碎片、装备材料、行动资源、公共事件贡献。任何新增资源必须写出稳定来源和消耗出口。

### 5.2 探索掉落与成长闭环

| 探索结果 | 主要奖励 | 回流用途 |
|---|---|---|
| 普通遭遇/战斗 | 经验、基础货币、常见材料；有明确概率与保底规则 | 升级、装备强化/制作、日常任务 |
| 稀有遭遇/首领线索 | 稀有材料、特殊装备/能力线索、里程碑记录 | 解锁高难度挑战、构筑差异和收藏目标 |
| 故事事件 | 个人旗标、故事记录、选择后果；必要时少量资源 | 打开本人后续分支、改变本人可见事件 |
| 调查/探索发现 | 线索、地点情报、图鉴或隐藏遭遇条件 | 提升后续探索的可读性和目标性 |
| 公共事件参与 | 参与凭证、贡献记录、阶段奖励 | 公共荣誉、赛季目标和有限度的资源奖励 |

原则：高价值成长不能只靠无限重复一个最低风险点；同时不以不可逆惩罚逼玩家在线。重复行为要有收益边界或递减，并为回流玩家保留稳定追赶方式。

### 5.3 故事选择与个人时间线

- 开局只展示征兆、传闻或互相矛盾的片段，不直接显示完整“克制表”和剧情答案。
- 通过探索、对话、图鉴、过往记录逐步补充证据；玩家能分辨“已知事实、角色猜测、未知风险”。
- 选择保存为玩家维度的剧情旗标和时间线记录。相同角色重复请求只产生一次后果。
- 后续事件读取该玩家自己的旗标决定选项、文本变体、NPC态度、遭遇或奖励；不读取别人的个人旗标。
- 分支以“分化一段、在关键节点重新汇合”为主，保留选择差异但避免分支数量指数膨胀。
- 重要选择前简短提示可能影响的范围（例如“影响你与某人的后续关系”），但不剧透具体结局。
- 写测试验证玩家 A 的选择不会改变玩家 B 的故事选项、奖励和结局。

### 5.4 故事/传说克制与战斗表达

**当前实施状态（2026-09-29）**：已停用“称号强/弱标签与怪物标签相同就固定增伤/减伤”的即时结算，旧 JSON 字段暂留兼容、不参与战斗。原著可以确认故事在具体情境中发生冲突接续、共鸣或吞噬（`txt/11.txt:3223-3227,3409-3413`），但不能由此推导 `reader→abyss→king→starstream→reader` 的普适克制循环；原文也明确否定仅凭故事/神话数量或位格压制对手（`txt/11.txt:14516-14520`）。这次改动是先撤销缺少证据的通用倍率，不代表条件化故事关系已经完成。

**下一步**：待阶段 3 的个人剧情旗标/调查状态稳定后，建立可审计的关系规则数据；每条规则必须指定适用遭遇、触发证据、提示等级、影响类型与上限、反制方式和来源分类（原著明示 / 游戏推导 / 尚未确认）。没有有效规则时保持中性倍率，并覆盖条件成立、缺线索、无关系、反制和玩家隔离测试。

故事克制要像“条件成立的叙事优势”，而非角色永久相克表。每次判定考虑：

1. 玩家实际拥有且已解锁的故事/能力；不能凭 UI 文案或客户端传参伪造。
2. 故事之间是否存在已被文本/设定证实的反制、上下位或冲突关系。
3. 当前场景、敌人阶段、角色是否满足该关系的触发条件。
4. 玩家是否做过相关调查，决定提示是明确、模糊还是未知。
5. 装备、技能、队伍配合是否提供了替代解法或减轻克制的方式。

结算需要保留“触发依据、影响范围、数值变化、反制方法”的可解释记录。克制影响设置上限，避免一次隐藏条件决定必胜/必败。具体权重和对照关系必须先根据小说文本与现有怪物/装备数据编表，再通过模拟测试确定；不在本计划中凭空写死数值。

原著证据与游戏推导候选映射已补入 [原著设定索引.md](原著设定索引.md) 第 4 节：第一项优先考虑个人剧情中“收集两段相关证据→出现一次接续/争取时间的后续分支”；“共鸣/吞噬”再考虑具体首领阶段危机；跨世界线暂时合流只进入共享组队/公共事件，不读取或覆盖他人的私有剧情。当前只有通用战斗位格修正，故事/传说标签不产生固定伤害克制；这几项映射属于游戏设计推导，尚未实现为新战斗数值。

### 5.5 共享大世界与公平参与

- 全服共享的是公共事件阶段、公开世界状态、广播和集体贡献结果。
- 每位玩家仍单独保存探索结果、掉落、战斗、故事选择和剧情进度。
- 公共事件必须有开放窗口/分阶段目标，让不同时间上线的人都能参与；不能因最早上线的一小群人永久关闭内容。
- 若事件改变地图/公共状态，记录变更版本和生效时间；个人剧情读取公共状态时采用明确规则，且重大内容提供回顾/补参与路径。
- 公共贡献奖励按有效参与和贡献区间计算，设上限并兼顾低位阶协助；禁止可交易资源形成刷小号或囤积优势。
- 老玩家影响世界的方式是增加共同成果、开启公共阶段、留下可见记录；不是替新玩家选择其个人剧情。

### 5.6 榜单、比较与追赶

建议先落地可解释的榜单，不把 PvP 分数和叙事成就混成单一总榜：

| 榜单 | 统计周期/公平方式 | 奖励方向 |
|---|---|---|
| 探索榜 | 周期内有效探索成果；按等级/位阶分组或计算效率 | 称号、展示框、少量通用资源 |
| 故事发现榜 | 新发现的线索/记录种类，不显示他人未公开的剧情答案 | 收藏展示、纪念称号 |
| 公共贡献榜 | 单次活动内有效贡献并按可参与次数归一化 | 活动荣誉、阶段奖励 |
| 秘境协作榜 | 完成难度、队伍协作与机制目标；不同难度分开比较 | 外观、记录、有限材料 |
| PK 榜 | 独立匹配分段和赛季结算；按匹配区间计算 | 赛季称号、外观、少量资源 |
| 收藏/图鉴 | 记录完成度，不把付费或随机次数直接等同于实力 | 收藏展示和非战力奖励 |

基础原则：榜单分赛季/周期；赛季奖励以称号、外观、展示和少量资源为主，不发能永久拉开差距的强力装备；为新玩家提供分组、回归任务、周期重置和参与奖励。个人具体剧情与他人榜单成绩无关。

### 5.7 日志优先、少弹窗

- 普通探索/战斗：主界面只给短提示；详细结果、消耗、掉落和状态变化进入分类历程。
- 关键剧情选择：弹窗承载阅读与选择；选择结果简洁确认，完整后果进个人故事卷宗。
- 首次获得稀有物、重要解锁、死亡/复归、重大世界事件：可用少量重要通知，不打断普通循环。
- 日志字段应至少包括：事件类型、来源/场景、发生时间、结果摘要、消耗、奖励、相关对象、关联请求/战斗 ID、个人/公共作用域。
- UI 上任何“获得/消耗”摘要都必须来自服务端结算结果，避免前端自己推算出与背包不一致的数字。

## 6. 分阶段实施顺序

### 阶段 0：建立基线与原著规则表

**工作项**

- 运行并记录当前前后端、数据库/本地游戏的启动方式和可访问地址；不对真实账号做消耗性测试。
- 给探索、战斗、故事选择、日志、奖励、排行和公共事件画出前后端调用链。
- 对照 `txt/1-10.txt`、`txt/11.txt`、`txt/12.txt`，整理“位格/属性/装备/技能/故事/克制”出处索引；把原著明示、游戏推导、尚未确认三类分开。
- 记录当前关键 UI 状态截图/测试数据，固定核心回归场景。

**验收**：有现状清单、原著规则对照表和可复现的主流程用例；没有根据记忆或猜测宣称某个设定为原著事实。

### 阶段 1：先修好探索—战斗—掉落—日志闭环（最高优先）

**工作项**

- 复测战斗按钮“持续战斗中/又回确认”问题，区分请求中、已结算、失败、待核实等状态。
- 统一探索事件、自动战斗结果、掉落和奖励写入日志的顺序与字段。
- 验证服务端幂等、防重复扣除/发奖/记账，前端刷新后能重新读到最终状态。
- 每次探索抽取结果（包括战斗遭遇）时统一扣一次该事件体力；迎战、撤退、网络重试和同请求键重放不得重复扣费。遭遇界面明确显示费用，并说明撤退不退已消耗的探索体力。
- 整理战斗日志：胜负、回合/关键过程、伤害摘要、消耗、经验与掉落；不把所有过程都做成阻断弹窗。
- 覆盖网络超时、错误响应、重复点击、刷新/重新进入、奖励为空和背包边界。

**验收**：一轮探索可走到最终奖励和历程记录；任意重复请求最多结算一次；界面不会永久显示加载或错误地再次询问是否开始。

### 阶段 2：资源经济与成长闭环

**工作项**

- 建资源来源—消耗—库存上限—回收表，标出探索、任务、战斗、商店、制作的流向；本轮静态基线见 [资源经济现状审计.md](资源经济现状审计.md)。
- 量化每 10 次探索、每小时恢复、任务/首领/PvP 等来源的预期资源变化，再复核经验曲线与消费出口；在完成量化前不凭感觉改产出数值。
- 评估离线恢复的经验收益和上限：当前休息 30 秒/经验、普通状态 90 秒/经验，需要决定这是预期挂机成长还是需要离线时长封顶。
- 整理属性职责、位格成长、装备/技能构筑的边界；先实现可读的成长说明，再调整公式。
- 让玩家能从日志看懂升级和构筑变化的来源；补新手期目标与回归追赶。

**验收**：每种重要资源至少有一个稳定来源和明确消耗出口；常见升级目标能通过正常探索达成；装备或技能变化可读且不会覆盖已有存档。

### 阶段 3：个人故事时间线与线索调查

**工作项**

- 统一剧情旗标命名、作用域、版本和写入方式；故事选择的请求也需幂等。
- 把“模糊预兆—收集证据—形成理解—做出选择—后续回响”做成可复用模板。
- 将个人选择结果展示在故事卷宗，并让后续探索/NPC/任务真正读取这些旗标。
- 用玩家隔离测试证明剧情和奖励不会串到其他玩家。

**验收**：同一事件重复选择不会重复奖励；玩家 A/B 的不同选择只改变各自可见内容；玩家能在日志回顾选择与已发生后果。

### 阶段 4：位格、能力、装备与故事克制

**工作项**

- 完成原著设定索引后，再确定游戏内属性/位格/能力的名称、边界和映射，不将猜测当作 canon。
- 建故事关系数据表：关系出处、适用目标、触发条件、可见提示级别、影响类型、上限和反制。
- 把当前称号叙事标签优势拆分成可解释的故事关系/条件判定；保留合理的位格差异，但避免单因素压倒构筑。
- 让装备、技能、调查和组队成为不同应对方式；日志写明发生的克制原因。
- 对相近位格、跨位格、无关系、条件未满足、反制成功等场景做战斗矩阵测试。

**验收**：每个生效关系可追溯来源且能解释；未解锁知识不在开局 UI 直接剧透；克制有上限、有反制、有测试样例。

### 阶段 5：公平榜单与玩家比较

- 先做榜单指标和周期定义，避免同一榜同时比较累计时长、数值战力和技术/故事发现。
- 规划分组、赛季快照、并列处理、防重复刷取和异常贡献校验。
- 首批上线探索、公共贡献、PK 等少量易解释分类；故事发现榜只暴露公开统计，不泄露剧情内容。
- 配套玩家自己的名次、差距、最近提升和可做目标，让榜单能转化为行动建议。

**验收**：老玩家累计存量不直接碾压新赛季；奖励不造成不可追赶的永久战力差；榜单有数据为空、并列、赛季切换和异常值测试。

**赛季 V1 方案（建议稿，未确认/未实施）**

- **周期**：建议每季 28 天（四个完整 7 日周），采用 `Asia/Shanghai` 固定边界 `[start_at, end_at)`；7 日滚动榜继续常驻，提供不必等到赛季结算的近期比较。
- **不重置长期积累**：不改角色位阶、等级、装备或 `rankings.rating`。赛季记录用独立 `season_id` 和结算快照，按结算发生时间计分；结算任务可重复执行但只能封存一次。
- **榜单分开**：PK 赛季榜只统计本季已结算战报的实际 ELO 净变化，展示胜场/场次并明确“包含所有 PK 模式”；故事榜只统计本季内首次完成、且此前从未完成过的 `event_key` 数量，公开页仍只显示数量、不公开故事内容。暂不做跨玩法综合总分。
- **暂缓不可靠类别**：近 7 日“探索行动榜”已经上线，但统计的是服务端接受的探索行动回执（含抽到战斗遭遇），不等于探索完成质量、胜率或角色实力，因此不直接拿来做赛季实力榜或发排名奖励。赛季探索榜仍暂缓，除非先明确有效完成/质量口径并验证反刷。世界首领贡献在逐次攻击流水缺失前只维持单场榜，不拼成跨赛季伤害总榜。
- **新人与奖励**：季中加入的玩家不回填加入前成绩；继续提供 7 日滚动榜作为即时追赶比较。建议首个周期仅展示/封存，不发排名奖励，观察参与人数、分数分布与对刷迹象后，再决定是否加入称号/外观等奖励及新人分组；不以强力装备或永久战力奖励排名。
- **待用户确认的关键项**：28 天周期是否合适；试运行开季日期；季中加入者仅依靠 7 日榜追赶，还是需要单独新人组；首个周期是否先无奖励观察。确认前保持建议状态，不创建赛季表、不改变现有奖励。

**V1 计分与封存细则（建议稿，仍未确认/未实施）**

- **赛季边界**：由用户确认一个开始日期后，在 `Asia/Shanghai` 的 00:00 开始；每季连续 28 个自然日，窗口一律采用 `[start_at, end_at)`，避免边界记录在相邻赛季重复计分。当前不预填开季日期，也不回填开季前成绩。
- **PK 赛季分**：只取 `pk_records.created_at` 落在本季且已结算的战报；每个玩家累加自己在 attacker/defender 对应的实际 ELO 变化，展示净变化、胜场和场次，并标注覆盖所有 PK 模式。名次只按净变化排序，同分共享竞赛名次；长期 `rankings.rating` 永不清零或改写。
- **故事赛季分**：每个玩家的每个 `event_key` 最多计 1；只有该玩家历史上首次完成的选择时间落在本季窗口才计分。公开榜只展示玩家公开名称、数量和名次，不展示故事键、选项、后果、奖励或个人结局。
- **暂不纳入季分**：探索行动继续只做近 7 日参与度榜，不把行动数冒充质量/实力；世界首领继续按单场活动排行，不从当前每场汇总记录拼造跨季伤害分。
- **新人追赶**：季中创建/加入的角色只累计本季实际发生的记录，不补历史分；首个无奖励观察季暂不拆新人组，以免样本不足造成榜单碎片化。玩家用常驻 7 日榜和个人位置接口查看近期差距。是否设置新人组留到观察参与分布后再决定。
- **封存与奖励**：赛季结束后生成 PK、故事两类独立结果快照；按 `season + category + player` 保证唯一，重复结算只能得到同一份封存结果，不覆盖旧季数据。首季只展示/留档，不发成长资源、称号或其他排名奖励；观测后再决定奖励和赛季是否继续。
- **实施验收门槛**：用隔离 H2 覆盖 `[start_at,end_at)` 两端边界、双方评分变化归属、首次故事发现与重复选择、同分名次、季中加入不回填、空榜/榜外个人位置、故事隐私字段、结算重复执行及旧季快照不可变；再以合成账号完成桌面榜单验收。门槛通过前不创建正式赛季数据、不连接真实玩家库。

**待推进**：故事发现、PK 表现和探索行动的近 7 日榜仍只是滚动窗口；探索行动仅衡量近期参与度，不是质量/实力榜。短期先在获准重启 3174 后检查并修复 PK/探索行动榜的运行态 HTTP 500，再做两个真实接口的只读验收（不连真实玩家账号、不触发游戏行动、不执行数据库迁移）。正式赛季已有一份具体但未确认的 V1 草案（周期、窗口、PK/故事计分、探索与首领排除、新人追赶、无奖励观察、封存及 H2 验收见上）；之后先确认 28 天周期、首季观察/奖励和是否分新人组，再实现独立赛季数据与幂等封存。公开贡献榜、秘境协作榜及其跨周期规则仍待设计。故事榜首次发现需要扫描完整历史；只有日志量证明成本不可接受后，才评估维护玩家—事件首次完成表。

## 7. 每轮开发的固定工作法

每次只交付一个可验收的小闭环，按以下顺序执行：

1. **定位**：读真实代码和数据，找出现有实现、调用链及对旧玩家存档的影响。
2. **写清规则**：先定义服务端结果、失败状态、幂等边界和 UI 表现。
3. **最小实现**：优先复用现有服务/面板；不把大规模重构与规则改动混成一轮。
4. **自动测试**：补服务层、接口层、前端状态和必要 E2E 测试。
5. **本地验收**：从玩家可见流程点一遍，确认资源、日志、状态三方一致。
6. **记录交付**：列出改了什么、如何验证、已知限制、下一轮具体入口；不把构建成功等同于功能验收成功。

涉及数据库写入、静态配置补齐、重启正在运行的服务或任何真实账号进度时，先区分影响范围；测试优先使用本地测试数据，不消耗真实玩家进度。

## 9. 风险与控制

| 风险 | 控制办法 |
|---|---|
| 当前工作区改动范围大、不同功能交织 | 先用现有分支和 stash 双重保留；每轮只改必要文件；不随意清理用户新增文件 |
| 小说事实、玩家推导、游戏规则混在一起 | 维护带章节/段落定位的设定索引；未核实内容标“待确认” |
| 个人剧情污染共享状态 | 数据层强制区分 `player-scoped` 和 `world-scoped`；补跨玩家隔离测试 |
| 重复请求造成重复扣费/奖励 | 服务端幂等键、唯一约束/结算记录和失败后的状态查询 |
| Spring 集成测试误连开发库 | 测试类固定 `test` profile、显式 H2 URL/驱动并断言数据源；不得从外部 `dev` 配置继承连接 |
| 多榜单变成刷次数比赛 | 限制有效次数、按周期/分段、归一化贡献、设置递减或上限 |
| 克制系统数值难懂或过强 | 记录触发依据、设置影响上限、准备反制路径并进行模拟测试 |
| 新内容压垮已有实现与老存档 | 先做迁移与默认值策略，测试旧存档读取和回滚路径 |
| 本地服务/测试账号误伤真实进度 | 使用独立本地测试数据；任何可能消耗真实账号资源的验证先停下确认 |

## 10. 暂不纳入近期范围

- 把移动端像素级重构与桌面端主流程修复混在第一轮。
